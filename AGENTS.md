# AGENTS.md — screenshot-rs-rebuild

## Project Identity And Purpose

- Rust rebuild of a **Wayland screenshot tool**, originally targeting niri; binary name `screenshot`.
- Upstream: `xander-lin/screenshot-niri`. The historical original-project path `/home/life/Work/screenshot-rs` is unavailable in this workspace.
- Launch is compositor-agnostic: do not gate on Niri session hints. Users test compatibility with their compositor's advertised Wayland protocols.
- Serves interactive screen capture on Wayland without external tools (no grim, no wl-copy, no shell-outs).

## Functional Goals And Scope

- **Normal mode** (default): freeze all outputs (with-cursor and cursor-free frame pair), dimmed drag-region selection overlay, save PNG, copy to clipboard. `1`–`9` full-screen capture, `H` toggles cursor in output, `L` promotes selection to long mode, `Esc` cancels.
- **Long/scroll mode** (`--long`): select a region on a single output, scroll content, continuous capture (configurable fps cap via `--fps`, default 30) with live stitched preview, direction hints (`Up`/`Down`/`Left`/`Right`), selection-box edit mode (`E`) with per-edge snap targets and wheel blocking for T/L-shaped captures and static-footer completion, finish on `Enter`/`Space`, stitch into one PNG (+ transparent corners for ragged shapes).
- **Clipboard**: `wlr-data-control` serving `image/png` (default) or `file://` URI (`--url`), as a detached provider process.
- **Output path policy**: temp dir default → `--file [PATH]` (Pictures/Screenshots) → `-o/--output PATH` → `--name NAME` → positional PATH (same as `--file PATH`).
- **Config file** (`~/.config/screenshot/config`): `max_fps` (default frame-rate cap when `--fps` absent) and `border_width` (visible selection-border thickness); optional, non-fatal, dependency-free parsing.
- Long-mode selections spanning outputs show a **white-red warning border**; releasing **discards the box** — the selection returns to empty and the user drags again, because long capture is single-screen and clamping would capture something they did not select. The same white-red colour marks a stitcher refusal — white mixed into red, everywhere a warning is shown. **Normal mode never warns about a spanning selection**: it composites per-output pieces, so spanning is a supported capture (during the drag, after release, and in edit mode alike).
- Edit mode supports edge resize and whole-box move (interior drag); captures are inset 1 logical pixel inside the box so the overlay border is never captured.
- Out of scope: X11, focus-grab extensions, diagnostics compatibility bins. Cross-compositor compatibility is user-tested.
- Out of scope: compensating for sticky headers/footers (`position: sticky` nav bars, frozen table headers, pinned footers). A selection that includes them is a user selection error; the stitcher does not detect, crop, or otherwise paper over them. Edit mode (`E`) is the sanctioned way to exclude them.

## Product Philosophy

- Pure Wayland-protocol clients; zero external command dependencies at runtime.
- Minimal dependency footprint (`libc`, `png`, `tempfile`, `wayland-client`, `wayland-protocols`, `wayland-protocols-wlr`).
- Stitching logic is deterministic, side-effect-free pure image code, heavily unit-tested; interactive/protocol code is kept separate from it.
- Frozen-screen selection UX: the screen freezes and dims during selection so the capture matches what the user saw.

## Project Principles

- Respect each module's boundary (see Module Contracts below) when changing interfaces.
- `found.md` holds durable project memory (module relationships, architecture decisions) and lessons learned; code is authoritative over docs — verify against code before relying on doc claims.
- Keep docs (`found.md`, `README.md`, `AGENTS.md`) in sync in the same change as behavior milestones (see the documentation-drift lesson in `found.md`).
- Verification: `cargo test` (unit tests live alongside modules; stitch has extensive pure-logic tests), `cargo check`, manual testing of Wayland flows under a live compositor. Performance changes additionally require `stitch-bench` before/after (three runs, same machine) plus unchanged corpora — see `docs/performance.md`.
- Long-capture performance protections must be preserved: configurable frame-rate cap (`--fps`, hardcoded default 30, range 1–240), damage-based capture after the first frame, near-duplicate frame skip (bypassed when the capture region changed), bounded capture channel backpressure, and capture pause during edit-mode edge drags.
- Selection-box edit mode (E key) semantics must be preserved: edges have snap targets only in edit mode; edit mode blocks wheel scroll by holding pointer input; frames captured after a resize are stitched at their deterministic known position; only the settled rectangle after an edge-drag release is captured. The drag is bounded by the whole desktop (`selection_drag_bounds`), not by one output, so a long-mode box can cross the seam and show the red warning; releasing such a drag **undoes it** (`settled_edit_rect` puts the box back where the drag started) instead of leaving a box that can never be captured. Normal mode keeps the dragged rect — spanning is a supported capture there. The render scope stays the selected output while the drag runs, so only that output's half of a crossing box (and its red border) is drawn; the other output keeps the frame it got at the `L` press. Do not widen the scope to draw the other half — the per-output pending-debt rule depends on it.
- Overlay buffers are never smaller than the content they display and never smaller than the output's pixel density: `max(content pixels, ceil(logical × preferred_scale / 120))`, where the content is the frozen capture when there is one and the output's current `wl_output.mode` otherwise (a `--long` session starts live, before any capture exists), with `buffer_scale` 1 and a `wp_viewport` destination equal to the logical size (`refresh_overlay_surface`). `wl_output.scale` is an integer hint and is never a logical-to-pixel ratio. Rendering works in buffer pixels and converts once: `draw_overlay_region` maps buffer to global logical for the hole/ring, `buffer_length` converts the configured border width, and the stitched preview is drawn buffer-major with a **direct buffer→canvas mapping** (buffer pixel to the selection's buffer extent, then the capture density; never through global logical coordinates, which quantises the phase to logical pixels and turns a 1:1 preview into a soft 1.5x upscale). Without `wp_viewporter` the buffer stays logical. Long screencopy requests use output-local logical coordinates; frozen-image crop rectangles use pixels.
- Capture exclusion lasts until frame completion, including after edit release. Border visibility is continuous during edits: any pending frame exposed to changed geometry is permanently invalidated and discarded before dedup/stitching, even if the box returns to its old position. PrepareCapture commits on the selected output and synchronizes the UI connection before acknowledging the worker.
- Live overlays share one renderer: cached dim mask/hole → stitched preview → selection border. The border is drawn last on every redraw and follows the current box, not the exclusion union. Both render paths take the warning colour from the same state decision (long-mode span / stitcher refusal); the frozen path must never hardcode white. A spanning normal-mode selection is not a warning state. Frozen and live paths use the same closed outside-ring pixel rule. Frozen dirty-region damage includes the full configured border width.
- The overlay hole is the **current** box united with the region of an in-flight capture, never the union of the drag trajectory: the dim edge must track the border in both directions, or shrinking stutters (border moves, dim stays). An in-flight frame prepared from a stale rectangle is invalidated (sticky) and its region is dropped from the hole during edit drags, so following the box cannot leak overlay pixels into accepted frames.
- Pressing `L` withdraws the frozen images at the key press itself: every overlay drops its frozen base and re-renders on the live path (dim + hole, real screen through the hole). The frozen frame must not survive into the session handover.
- Memory: overlay buffers are full-resolution RGBA per output, **2 each** (one on screen, one committed and awaiting display) plus a base-pixels cache; footprint is resolution-driven, not fps-driven. Two is enough because the overlay only commits when its content changes, and the only screen that streams is the one long capture is scoped to — measured on niri 26.04 with two 1920x1080 outputs, a full `--long` session completes on two. A third buffer was previously reserved against a compositor that holds a buffer for a whole frame; that has not been observed, and if one is ever found `OVERLAY_BUFFER_COUNT` is the constant to raise. At the `L` handover the **other outputs' buffers are released** (`buffers.clear()`): long capture is single-screen, those surfaces are never committed to again, and each held set is 8.1 MB. Measured: 4 buffers / 32.4 MB `RssShmem` during selection → 2 buffers / 16.2 MB while capturing.
- The frozen selection is stored **once**: the without-cursor capture, plus a `CursorDelta` patch holding the pixels where the with-cursor capture differs (measured 1 440–2 706 of 2 073 600 pixels, 0.07–0.13%, i.e. a mouse-pointer-sized patch instead of a second 8.3 MB frame — and zero on an output the cursor is not on). `H` toggles whether `frozen_pixel` applies the patch, so it costs no rebuild. The patch records *every* differing pixel rather than assuming "only the cursor", so a caret that blinked between the two captures is reproduced exactly. The overlay's render cache is geometry-only (`width`, `height`): both pixel layers it used to precompute are derived per draw from that one stored frame. Session resident (normal mode, two 1920x1080 outputs): 124.7 → 51.8 MB.
- A long capture's canvas is stored in 64-row tiles and **packed when cold** (`stitch::store`): a session keeps every pixel it has stitched (16.6 MB on `real-1`, 35.0 MB on `real-long`) while the stitcher reads only the previous viewport and the overlay displays at most one screenful. Measured resident canvas: 16.6 → 3.8 MB and 35.0 → 9.5 MB (lz4, ratio 5.5% / 9.1%); session resident 40.3 → 6.9 MB and 87.6 → 21.0 MB; peak 62.1 → 11.1 and 133.8 → 34.9 MB. The packing is a build-time choice (`canvas-raw-tiles` keeps everything resident, the pre-compression behaviour) and correctness never depends on it. Two rules make it work and must not be collapsed: a row is **only** readable where a frame actually wrote it (a tile is allocated whole, so its tail rows are not content — reading them as zeros made the colour check compare a frame against black), and growing the canvas **upward relabels the grid** instead of re-cutting it (the contiguous buffer this replaced copied every pixel on every prepend, which is where its 2× peak came from). The live preview is likewise a **window** of the canvas (`CanvasWindow`: one viewport of reach each way), not a full RGBA copy of it — that copy was 22 MB and 46.5 MB per frame for pixels the overlay could not address.
- Overlay presentation follows the commit-on-change contract: a buffer already showing the current rect and preview seq is never re-committed, so steady-state long capture issues zero commits and capture throughput never depends on compositor release timing.
- Long capture is single-screen by construction: at the frozen→live transition the render scope narrows to the selected output (`UiState::render_scope`), and overlay rendering, the pending-render debt, and its clearing count in-scope overlays only. The other outputs' overlays keep the live dim frame rendered at the `L` press (never a frozen image — see above). Never widen the debt condition back to all overlays — an all-overlays clearing condition is unsatisfiable when each output's canvas turns over independently.
- Prepare must never abandon capture frames: transient all-canvases-held states right after a drag burst are normal (releases are in flight); the per-frame recovery path must always flush and read the socket so releases get processed. `dispatch_poll`'s early return (`dispatch_pending > 0`) deliberately skips flush/read and must not be the only path a recovery depends on.

## Module Contracts

Concise boundaries for each module: what it owns, what it must not do, and how it is verified.

- **`config`** — Owns optional user settings (`max_fps`, `border_width`) from `$XDG_CONFIG_HOME/screenshot/config`; parses `key = value` lines with `#` comments and clamps ranges. Must not parse CLI args or touch Wayland. Malformed/unreadable files degrade to defaults (never fatal). Verified by unit tests for parsing and range clamping.
- **`cli`** — Owns flag parsing, invalid-combination rejection, output-path resolution, and help/version text. Must not touch Wayland, write images, or serve the clipboard. Failure: unknown flags, missing values, unsafe temp dir, invalid `--name`, out-of-range `--fps`, mutually exclusive output modes. Verified by parsing/path unit tests.
- **`app`** — Orchestrates freeze → select → composite → write → clipboard, and long capture (fps-capped worker, PrepareCapture handshake on the exact clean-render rectangle, offset-aware stitching). Launches without compositor-name gating. Must not implement protocol dispatch or PNG encoding. Screen-space capture regions use output-local logical coordinates; stitch offsets use returned-frame pixels. Discard edit-invalidated frames before dedup/stitching. Verified by integration/manual test under a live Wayland compositor and `cargo check`.
- **Output geometry is N-way, never two-way** — every rule is written over `outputs` as a collection: offsets are accumulated across all covered outputs (`scaled_axis_offset` sorts intervals and sums the spans before each piece), `full_output_rect_by_index` sorts by `(x, y)`, and no code indexes `outputs[1]` or tests `len() == 2`. Verified by unit tests for 1, 3 and 4 outputs, stacked and negative-origin layouts, and mixed scale. **Known limitation**: mirrored/clone outputs share one logical rectangle, so `rect_spans_outputs` reports every selection as spanning; long capture therefore refuses on that layout (`--long` cannot work on a clone pair, and normal mode still composites correctly). Position comes from `OutputPositionSource`, which prefers `zxdg_output_v1.logical_position` and falls back to `wl_output.geometry`'s `x`/`y` — without the fallback a compositor lacking the xdg output manager left every output at the `(0, 0)` seed, collapsing a multi-screen desktop into one rectangle.
- **`geometry`** — Converts logical selected rectangles into per-output capture regions; clamps a spanning normal-mode selection to the drag-start output (`clamp_rect_to_output_at_point`, largest-piece fallback) when it is promoted with `L`. Crop rectangles derive their pixel ratio from the capture itself (`image.width / output logical width`, edges mapped and destination offsets anchored at the same output origin, so each offset equals the widths already written and adjacent pieces stay contiguous) — never from `wl_output.scale`, which is an integer hint: on a 1.5 output reporting 2 it asks for pixels the capture does not have and the whole normal-mode composite is abandoned. No pointer input, registry handling, or pixel copying. Verified by intersection/scaling/mixed-output unit tests.
- **`image`** — Represents SHM images, converts XRGB/ARGB8888 to RGBA PNG, and blits regions. No Wayland capture, path policy, or clipboard ownership. Verified by blit/format unit tests.
- **`stitch`** — Placement goes through `PlacementEngine` (`src/stitch/engine.rs`): the production `WindowedEdgeMatcher` compares boundary positions (48 column bins of quantised `|dL/dy|`), places each frame with exactly three searches and refuses when all three fail. **Impulse**: the neighbourhood of where the last step points (`pos + last delta + trend`), radius `max(24, 1.05×|last delta|)`; 1.10 is measured to break (it catches jump frames the guard places better). **Guard**: is this frame the next step of the capture? Only positions that still *overlap* the previous frame qualify — `pos ± rows`, symmetric, a property of the two frames and never of the canvas. It is `rows`, not `rows − minimum_overlap`: overlap and evidence are different questions, and folding the quality gate into the window made the window a constant of the gate rather than of the frames. Both directions are ordinary — a scroll-back is predicted, guarded and placed exactly like a scroll-down (real-1 scrolls up, −8020 px total, 112 negative steps). **Anchor**: does this frame appear anywhere the canvas can see? The whole canvas, nearest-first from the last confirmed position, skipping the guard band. It runs **whenever the guard has nothing**, not only after the border turns red: a frame that shares no rows with the one before it has no local answer at all — no guard position can even be scored — so waiting is not safer (the frame is further from where it was captured, not closer), and the wait never ends when the box is shorter than the scroll step, where *every* frame is a jump (measured before the change: 8 pending, 1 recovered, 8 pending again). `REFUSAL_PATIENCE` stays where it belongs: the border and the frame-rate drop. Overlapping positions are re-*judged* by each stage but not re-*computed* (`ScoreCache`, one per `place`). The guard needs no ladder — its window is one interval — while the anchor's rings start at one viewport (`rows`) and grow ×4, so every ring size comes from the frame rather than a configured constant (fixed-width bands were measured to lose 58 acceptances and add 13 misplaced writes on real-1). The engine stores **logical** canvas rows only: `commit` receives `requested_top` (logical) alongside the pixel canvas's re-based `rect.y`, and every write, `pos`, `anchor` and delta uses `requested_top` — mixing the two silently stops the canvas from growing when a frame extends it upward. `EdgeCanvas::shift_forward` re-bases `origin_row` only; the covered logical extent does not move. There is no displacement cap and no refusal-widening: what a frame may match is decided by how much evidence the canvas can still supply, and the ring ladder makes a far answer only reachable after every nearer ring has failed; `LegacyPipeline` (feature `stitch-legacy`) keeps the old canvas scan for A/B; `ScriptedEngine` is the test mock. Gates are calibrated on **real browser frames**, not the synthetic corpus — see `docs/edge-stitch-design.md` §12. They must not depend on the search window: `best/median` did and was removed (the same winner read 0.731 in a ±36 window and 0.488 in ±1400). What decides now: an evidence floor `used >= min(3, the frame's own boundary rows)` — relative, because a frame cannot be asked for more rows than it has: a page whose only feature is one gray-to-gray boundary is held to that one row (its frames stitch; frames that are pure flat gray carry no boundary at all and are honestly refused), while a dense frame overlapping the canvas by a sliver still needs three, which is what refuses jump frames whose single comparable row lines up (lowering the constant to 1 instead measured 204→201 accepted and 0→6 misplaced on real-1); winner cost ceiling `EDGE_MAX_ACCEPT_COST = 0.08`; runner-up ratio `second/best ≥ 2.5` forgiving a high winner (motion blur genuinely weakens boundaries, real-long reaches 0.168 — and `second = None` reads 0, so an empty window cannot claim the escape); and a **colour verification of every acceptance** against the pixel canvas (ceiling 30, between real content in motion at 40.6 and an unrelated structural fake at 82.2) because the ladder is colour-blind by design and that blindness lets colour-swapped repetitions pass structurally. Ties (`second/best < 1.5`) resolve by the colour check first, then nearest to the window centre; a winner costing exactly 0 reads as infinitely ahead, not as a tie. Two further guards: a basin of viewport/8 when looking for the runner-up, and a count of distinct equally-good candidates — rivals are the candidates within the same `second/best < 1.5` test that makes a frame ambiguous, so one definition decides both. A single refusal reports `PushResult::Pending` (border unchanged, full frame rate); `REFUSAL_PATIENCE = 8` consecutive refusals are required before `NoMatch` turns the border red and drops to 5 fps. **Axis routing**: the axis is the capture's impulse — the last accepted step — not the arrow key. The hint only seeds the very first frame and supplies the *direction* of a fallback attempt. A **geometry edit is a known step**, so it records its direction too (`push_geometry_frame`): after the box is nudged sideways, the next frame is looked for horizontally even though the arrow key still says "down"; a resize (delta 0) says nothing and clears that memory. A geometry edit is **known**, so it also keeps the matcher's canvas unless it changed the descriptor's geometry: a width change or a horizontal move re-cuts the bins (or compares different columns), while a height resize or a vertical move leaves every stored row — 48 bins across the frame's width — valid. Resetting on every edit threw the whole history away, and a box shrunk below the scroll step then had neither a local answer nor an anchor to recover from, so the capture stalled for good (every frame pending, preview frozen). `commit_known_step` writes the edited frame without folding the box's own move into the scroll-step memory (`last_delta`/`trend`), which a resize would flatten to zero and a move would point at the box instead of the content. When the layout *did* change, the rows are not simply lost: `reseed_from_canvas` rebuilds them from the pixels the canvas already holds (`EdgeLadder::from_source` over `CanvasRegion`, in 512-row bands with one row of margin so every kept row's gradient is the one a full-frame ladder computes), skipping bands whose rows do not cover the whole new x range — a row captured at another column would produce a descriptor from zeros, and a zero row marked filled scores every later frame against black. The impulse axis is asked first; if it cannot place the frame, the other axis is asked **once**, and the two answers are never scored against each other. **"Nothing moved" does not count as an answer on the impulse axis** while the duplicate check has already shown the pixels changed: a zero-delta placement asks the other axis too, and is kept only when that axis has nothing better (content that genuinely changed in place). This is what a stale impulse looks like at a turn — the axis the capture just left keeps answering zero, because movement along the other axis barely disturbs its descriptor, and the colour check does not catch it (measured: 26.78 against a 30 ceiling for a 240 px vertical step on the snake page). The **horizontal** fallback runs only when the user indicated a horizontal direction (nothing about the content says which side it moved to); the vertical fallback is symmetric like the guard, because a scroll-back is an ordinary step. There is no geometric short-circuit before the fallback: the previous frame's rectangle is inside the canvas by construction, so "no overlap" is a pixel question the search has to answer, not a rectangle test. No fallback means the frame is refused.

**The horizontal axis is the same matcher, built on demand.** It keeps no state: a horizontal step is rare, and a persistent second canvas would need re-seeding on every vertical step anyway. `place_horizontally` builds the descriptor for the one region the comparison may use — **the previous frame's own rectangle**, captured by construction because that frame wrote it — and runs the same `decide`/`decide_from_costs` gates on it. The strip must be the previous rect and not "everything the search can reach": on a ragged canvas the wider strip contains never-captured columns whose zero bytes corrupt the descriptor, and the first left step of a snake is then refused. Both directions are ordinary on the impulse axis (a scroll-back is a step like any other, so the window is `previous ± one frame width` and symmetric); as a fallback it searches only the indicated side. It has **no anchor window** — recovery belongs to the axis the capture is on. The comparable part is exactly the overlap with that strip; pixels nothing has captured are never read. The vertical engine still **re-seeds** after a horizontal placement (`reset`, then `commit` at the frame's own rect): `EdgeCanvas` is **one column** of binned rows and `commit` ignores `rect.x`, so its rows describe whichever column captured them first, and the next vertical step must read the new column. This is what lets a **serpentine** capture work: right, down, left, down … growing the canvas on both axes and handing the scroll axis over at each turn; without the re-seed the first vertical step after a horizontal one is refused, and without the previous-rect strip the first left step is refused. Both are pinned by `a_snake_path_reconstructs_a_page_wider_than_the_viewport` and `a_snake_path_works_on_a_wider_page_with_quarter_overlap`, which assert every delta and compare the finished canvas to the page pixel for pixel. Also deterministic multi-stage matcher plus offset-tagged geometry placement: changed offset/size places a frame at its known position, growing ragged T/L/arch canvases with per-row coverage (uncovered extents transparent). Two rules follow from "ragged" and must not be collapsed: (1) being inside the canvas **bounding box** is not being captured — a frame may land in a never-captured region (the leg of an L, the space between the legs of an arch) and must still be appended, otherwise its pixels are dropped while it is reported `Accepted`; (2) the colour check compares only pixels the canvas actually captured, because never-captured bytes are zero and reading them measures the frame against black — on a snake canvas a left step overlaps the region it has not captured yet, and scoring that region makes the correct placement cost too much to accept. Coverage is `RowCoverage::{Empty, Full, Spans}` per row: `Full` keeps the rectangular case allocation-free, `Spans` carries *disjoint* extents so an arch's gap stays transparent (a hull painted it opaque), and `Full` resolves against the width the row was written at, not the current one. Must not handle CLI, Wayland, scrolling, output selection, PNG writing, or sticky-header/footer compensation (see Out of scope). Preserve covered pixels (not the bounding rectangle) so later widening fills recaptured strips; never-captured strips stay transparent. Pixels live in `stitch::store::CanvasStore`, not in a `Vec<u8>`: 64-row tiles, packed when cold by a `TileCompressor` (lz4 by default, `canvas-raw-tiles` for the uncompressed baseline), with a working set bounded by a budget that scales with the frame. Read it only through the accessors (`pixel`, `row_into`, `region_into`); a `StitchedFrame` is deliberately `!Clone`. A seeded randomised group (`tests::random_sessions`) walks random multi-step sessions — a random initial selection, random box drags and resizes, random scrolling on both axes, and paths that cross themselves — asserting every step's delta and the finished canvas pixel for pixel (never-visited rows and columns stay transparent); it is gated off for `stitch-legacy`, whose A/B scan refuses steps the shipped engine places. Verified by the extensive stitch unit tests plus the real-browser corpus.
- **`clipboard`** — Serves `image/png` or file URI via `wlr-data-control`. No region selection, capture, or path decisions; no external clipboard commands. Verified by manual paste tests under a live Wayland compositor.
- **`wayland::screencopy`** — Binds wlroots screencopy and captures outputs into SHM buffers (one-shot frozen + persistent long-capture session). Requests use output-local logical regions; persistent capture returns `None` on cancellation. No selection UI, PNG writing, or stitching. Damage waits poll a stop flag with bounded latency so joining the worker never requires fresh damage. Verified by manual capture plus `cargo check`.
- **`wayland::selection`** — Layer-shell overlay: dimmed frozen frames, visible border, drag/edit interactions, long-mode preview/status, and live selection/output accessors. Overlay buffer size is the `max(capture, density)` rule above, refreshed from the layer-surface configure and from `wp_fractional_scale_v1.preferred_scale` (either can arrive first); the buffer is not resized at the `L` handover, so the live path keeps the dense buffer. Caches only dim/hole; composites preview then border every time. Frozen and live borders share one closed outside-ring rule (corners, configured width); frozen damage includes the ring. `prepare_capture_clean` commits on the selected output and roundtrips before acking; `complete_capture` rejects any frame exposed to a geometry change (sticky), which `app` must discard. No focus-grab extensions or compositor-name checks. Verified by overlay-pixel/dirty-region/edge unit tests plus manual drag-selection and edit-mode tests.
