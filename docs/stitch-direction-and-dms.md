# 拼接机制：与 DMS 正面对比 + 单方向/双方向边界实验

- 日期：2026-10-18
- 前置：`docs/edge-stitch-design.md`（机制设计）、`docs/dms-stitch-comparison.md`（早期源码级对比）
- 本文回答三个问题：
  1. 我们只用了横向边界还是纵向边界？有必要测两种吗？
  2. 现在是什么状态？完美吗？
  3. 和 DMS 的实现对比如何？

## 1. 只用了哪个方向的边界

**只用了横向边界**（`|dL/dy|`：某一行与上一行的亮度差）。纵向边界（`|dL/dx|`：某一列与左一列的亮度差）从未参与匹配。

这是有意的：长截图只沿垂直方向滚动，横向结构在整个会话中**不随滚动变化**，所以它不携带位置信息；只有随滚动移动的横向边界才能定位。

但这个论证只在「横向结构不随滚动变化」成立时有效。有两种情况会破：

- 页面有横向动画（轮播、视频、进度条）；
- 页面某区域横向结构极强而纵向极弱（竖直分隔线、侧边栏、宽表格的列线）。

所以必须实测，不能只靠论证。

## 2. 单方向 vs 双方向：实测

### 2.1 正常网页内容：三种描述子完全等价

同一批帧（5 个页面 × 12 组真值），同一门限、同一搜索（`study_dir.py`）：

| 描述子 | 每行值数 | 正确 | 错误 | 红框 | separation p5 |
|---|---|---|---|---|---|
| H（仅横向） | 48 | 60 | 0 | 0 | 0.97 |
| V（仅纵向） | 48 | 60 | 0 | 0 | 0.98 |
| H+V 拼接 | 96 | 60 | 0 | 0 | 0.98 |
| H+V 融合（逐 bin 取大） | 48 | 60 | 0 | 0 | 0.98 |

**在正常网页上，两个方向都能独立完成定位，没有任何一个方向更好。** 原因是正文、表格、卡片都同时具备两种边界：文字行有基线（横向），文字块和列分隔有左右边缘（纵向）。

### 2.2 退化内容：各自的方向盲区

构造只保留一种方向信息的页面（`study_dir2.py`）：

| 页面 | 特征 | H 的边界行数 | V 的边界行数 | H 结果 | V 结果 |
|---|---|---|---|---|---|
| vstripes | 竖条纹，纵向完全均匀 | **0** | 700 | 无候选 | 歧义（sep=0） |
| hstripes | 横条纹，横向完全均匀 | 16 | **0** | 480（错，真值 120） | 无候选 |
| tallgrid | 高单元格表格（行高 220） | 18 | 694 | 120 ✓ | 120 ✓ |
| gradient | 纯纵向渐变 | 0 | 0 | 无候选 | 无候选 |
| narrow-col | 760 px 正文 + 大量留白 | 53 | 376 | 120 ✓ | 120 ✓ |

两条结论：

1. **单方向确实存在盲区**，但盲区出现在「另一个方向完全无信息」的合成内容上。真实网页不会出现纯竖条纹。
2. **双方向不能修复歧义**：vstripes 上 V 有 700 行边界，仍然 `sep=0`（所有偏移看起来一样，因为每行完全相同）。加 H 也没用（H 在那里是 0）。**歧义是内容属性，不是方向数量问题。**

### 2.3 噪声下的鲁棒性

`study_dir3.py`，噪声 σ 从 0 扫到 10（正确/9）：

| 页面 | 描述子 | σ=0 | σ=4 | σ=6 | σ=10 |
|---|---|---|---|---|---|
| tallgrid | H | 9/9 | 9/9 | 9/9 | **9/9** |
| tallgrid | V | 9/9 | 9/9 | 9/9 | **0/9** |
| tallgrid | H+V | 9/9 | 9/9 | 9/9 | **0/9** |
| narrow-col | 全部 | 9/9 | 9/9 | 9/9 | 9/9 |
| doc | 全部 | 9/9 | 9/9 | 9/9 | 9/9 |

**关键发现：在 tallgrid 上，加 V 反而让高噪声下的表现从 9/9 掉到 0/9。**

原因（实测曲线，`tallgrid`，s=120）：

| 偏移 t | V 的代价 | H 的代价 |
|---|---|---|
| 1 | 0.0484 | 0.9973 |
| 40 | 0.0471 | 0.9973 |
| 118 | 0.0107 | 0.6298 |
| **120（真值）** | **0.0000** | **0.0000** |
| 300 | 0.0470 | 0.9948 |
| 500 | 0.0437 | 1.0000 |

V 的代价在整个范围内只在 **0.000–0.055** 之间波动（spread 0.055），而 H 在 0.000–1.000 之间（spread 1.000）。也就是说，V 在这个页面上几乎没有区分度——它给每个候选位置都打了「差不多」的分。把这样的信号与 H 平均，等于把 H 的尖锐度稀释了：

```
V 单独:  sep = 0.491   (σ=10)
H 单独:  sep = 0.990
H+V   :  sep = 0.769   ← 比 H 单独更差
```

**所以「多一个方向」不是免费的鲁棒性，它可能引入一个低区分度的稀释项。**

### 2.4 端到端（与 DMS 同一 harness）

同一 720 帧、同一门限、只换描述子方向（`DIR=H/V/HV`）：

| 方向 | 接受 | 跳变 | 拒绝 | 严格覆盖率 | ms/帧 |
|---|---|---|---|---|---|
| H | 490 | 2 | 230 | 58.6% | 13.2 |
| V | 489 | **1** | 231 | 58.6% | 14.0 |
| HV | 490 | 2 | 230 | 58.6% | 14.2 |

差异在噪声内（跳变 1 vs 2 是单帧事件，见 §4.2）。**在真实网页语料上，方向选择不影响结果；在退化内容上 H 更稳；在理论上 V 能补 H 的盲区，但真实网页没有那种盲区。**

### 2.5 结论

**保留单方向（横向），不实现双方向。** 理由按强度排序：

1. 真实网页上无收益（§2.1、§2.4）。
2. 引入低区分度方向会稀释 separation，在高噪声下更差（§2.3）。
3. 成本翻倍（描述子 1.82×，每行值数 96）。
4. 唯一理论收益是「纯竖条纹页面」，而这类页面本身也没有滚动可拼的内容。

**但要把这条写成可证伪的约束**：如果将来遇到「纵向结构极弱、横向结构极强」的真实页面（例如纯色背景 + 竖直分隔线的看板），需要重新评估。这不是现在要解决的问题。

## 3. 现在是什么状态

**不是完美状态。** 分三块讲。

### 3.1 已达成

| 指标 | 现有实现 | 本设计 |
|---|---|---|
| 静默错位（内容被放到错误位置） | 254 帧（480 帧口径） | **2 帧**（720 帧口径） |
| 显式失败态 | 无 | 有（红框 + 冻结锚点） |
| 跟踪态单帧 | 32.6–76.4 ms | 3.0–3.9 ms |
| 半行滚动 | 5–23 帧静默 | 0 |
| 稀疏页面 | 无此概念 | 与密集页无差异 |

### 3.2 未达成

1. **仍有 2 帧静默错位**（§4.2 有逐帧分析），不是 0。
2. **代价高**：harsh 模式 20.3 ms/帧，DMS 是 3.6 ms。原因是窗口内逐行扫描（§4.4）。
3. **拒绝率偏高**：harsh 模式 230 次拒绝（DMS 88 次），意味着用户会看到更多红框。这些拒绝里 **0 次是「本可匹配却拒绝」**（§4.3），全部是无重叠帧——但用户体感是「红框很频繁」。
4. **横向滚动未测**（按决定推后）。
5. **周期内容理论上仍可骗过**：separation 是概率防线，不是证明。
6. **`MIN_USED` / `SEP` 是经验阈值**，不是推导值。

### 3.3 一句话

**核心目标（不再静默错位）基本达成（254 → 2），但代价、拒绝率和 2 帧残留都还没到「完美」。**

## 4. 与 DMS 的对比

### 4.1 方法

- DMS 侧：`stitch.go`（407 行，v1.6.3 原样）+ `scroll.go` 的状态机（重复帧检测、`unmatchedTicks`、`seamAppend`），Go 复现，只加了导出包装，**逻辑零改动**。
- 本设计侧：同一 harness 内独立实现（48 列边界阶梯 + 三段窗口 + separation 门限）。
- 同一批帧、同一随机种子、同一噪声（σ=1.5）、同一真值。

**指标定义**（关键，避免把「丢帧」误算成「错位」）：

- `jumps`：相邻两个接受帧的画布偏移发生变化 → 内容被放到错误位置（**真正的损坏**）
- `gaps`：有可用重叠却拒绝 → 丢内容
- `refused`：无重叠而拒绝 → 正确行为
- `captured`：落在正确画布位置的行数
- `ms/frame`：建描述子 + 匹配（两侧口径一致）

### 4.2 总体结果

720 帧（6 页面 × 5 模式 × 24 帧）：

| 实现 | 接受 | **跳变** | 丢帧 | 拒绝（无重叠） | 严格覆盖率 | ms/帧 |
|---|---|---|---|---|---|---|
| DMS | 630 | **90** | 2 | 88 | 55.9% | **2.55** |
| 本设计 | 490 | **2** | 0 | 230 | **58.6%** | 13.4 |

**DMS 的 90 次跳变全部来自 `seamAppend`**：`scroll.go:560-570` 在「连续 4 次 unmatched tick」后，把当前帧直接追加到画布末尾，不验证任何重叠。这在设计上是「跳跃后重新起一段」，但产出物是**一张中间有隐形接缝的图**，用户看不到任何提示。

典型样例（`cards2 burst`）：

```
truth=3380 placed=1969   (差 1411 = 卡片周期的整数倍)
truth=3510 placed=2099
truth=3640 placed=2229
```

每帧都「成功接受」，画布每帧都增长，但整段内容被放在 1411 行之前。**这正是本项目要消灭的失败模式。**

本设计的 2 次跳变（全部在 `cards2 burst`）：

```
truth=3380 placed=1969   prev_offset=0
truth=1941 placed=-646   prev_offset=0
```

两者都是**周期内容的整数倍错位**（1411 和 2587 都是卡片周期的倍数），且都发生在「前一次接受之后紧跟一次大跳」的边界上。**这是本设计已知的残留缺陷，不是意外**（§4.5）。

### 4.3 拒绝是否合理

本设计的 230 次拒绝中：

- **230 次是「无重叠」**（长跳 560–1500 行，视口只有 700 行，物理上无法匹配）
- **0 次是「本可匹配却拒绝」**

DMS 的 88 次拒绝中 86 次无重叠、2 次本可匹配（DMS 丢掉 2 帧可匹配内容）。

所以拒绝率高不是「过度保守」，而是**长跳场景下唯一正确的行为**。DMS 之所以拒绝少，是因为它用 `seamAppend` 把无重叠的情况「假装解决」了——代价是 90 次跳变。

### 4.4 性能差距的归因

本设计 13.4 ms/帧 vs DMS 2.55 ms/帧（5.3×）。分阶段实测（720 帧累计 9032 ms）：

| 阶段 | 耗时 | 占比 | 位置数 | 每帧位置数 |
|---|---|---|---|---|
| 冲量窗 | 1228 ms | 13.6% | 166299 | 231 |
| 宽窗 | 4035 ms | 44.7% | 594618 | 826 |
| 锚点窗 | 3770 ms | 41.7% | 1293831 | 1797 |

**85% 的时间花在宽窗和锚点窗**，而这两个窗口只在「冲量失败」时触发——也就是长跳帧。DMS 在这些帧上不搜索（直接 `seamAppend`），所以快。

换句话说：**性能差距不是实现效率问题，是「愿不愿意花时间确认」的选择**。DMS 选择不确认（跳变 90 次），本设计选择确认（跳变 2 次）。

优化空间（**[推断]**，未实测）：

- 宽窗/锚点窗加粗筛（但 §2 的 `study12.py` 显示粗筛在周期内容上召回 0–33%，会重新引入跳变）；
- 窗口内用 SIMD / 位运算（48 列 × 3 级 = 可打包进 2 个 u64，一次比较 8 个位置）；
- 红框后降频到 5 fps（已决定），直接把这部分成本摊薄 6 倍。

### 4.5 DMS 值得借鉴的地方

1. **`stitchActivityMin`（活动行）**：DMS 只用「与上一行有差异」的行参与匹配（`stitch.go:132-140`），并且要求 `activeMatches >= stitchMinActive`（12 行）。这与本设计的「可比较边界行数 ≥ 8」是同一个思想的两种写法。**DMS 早就做了这件事**，只是阈值固定。
2. **`stitchPredictWindow = 160`**：DMS 的预测窗口固定 160 行，本设计是 `max(24, 0.6Δ)` 自适应。DMS 更简单，本设计对快速滚动更宽容。
3. **`stitchMaxCanvasBytes = 256 MiB` / `stitchMaxRowsCap = 30000`**：本设计仍未加画布上限（`docs/dms-stitch-comparison.md` 已列为待修）。

### 4.6 DMS 明确不做、我们也不该做的

- `matchIgnores`（顶部 10% / 底部 8% 忽略带）：这是粘性页眉页脚补偿，已按产品决定列为 out of scope。
- `seamAppend`：**不借鉴**。它把「无法确定」变成「静默接受」，正是本项目要消灭的行为。

## 5. 待办与优先级

| 优先级 | 事项 | 依据 |
|---|---|---|
| P0 | 修 `NoMatch` 推进参考帧（教训 14） | 独立缺陷，与新机制无关 |
| P0 | 实现新匹配器（48 列边界阶梯 + 三段窗口 + separation） | §4.2 |
| P1 | 红框状态 + 5 fps 降频 | §4.4（摊薄 85% 的宽窗/锚点成本） |
| P1 | 画布上限（256 MiB / 30000 行） | 借鉴 DMS |
| P2 | 消除 2 帧周期错位 | §4.2，需要额外信号（见下） |
| P2 | 宽窗/锚点窗的位运算加速 | §4.4 |
| P3 | 横向滚动 | 已决定推后 |

**关于 P2 的 2 帧**：两者都是周期内容的整数倍错位，`separation` 没能拦住。可选的额外信号：

- 跳变前强制要求「连续 2 帧一致」——第一帧先记为候选，第二帧确认后再写入画布。代价是每帧延迟一拍。
- 对「位移是内容周期整数倍」的情况降级为红框（需要先估计内容周期，成本较高）。
- 接受它：2/720 = 0.28%，且用户可以靠红框缺失+肉眼看出来。**[推断]** 这是最可能的选择。

`/tmp/opencode/`（tmpfs，重启即失）：

| 路径 | 内容 |
|---|---|
| `edge-study/study_dir.py` | 单/双方向在正常内容上的对比（§2.1） |

| `dms-src/` | DMS v1.6.3 `stitch.go` / `scroll.go` 原样 |

harness 用法：

```
cd /tmp/opencode/dms-cmp && go build -o cmp .
./cmp                                  # 全量对比（§4.2）
DIR=V ./cmp                            # 换方向（§2.4）
SEP=0.90 MINUSED=32 ./cmp              # 门限消融
BREAKDOWN=1 ./cmp                      # 阶段耗时（§4.4）
VERBOSE=1 ./cmp                        # 逐帧跳变明细（§4.2）
```

DMS 侧改动只有三处：加 `clamp`（从 `region_render.go:901-909` 原样复制，同 package）、加导出包装、`Stitcher` 类型别名。**拼接逻辑与状态机零改动。**

## 7. 一句话总结

- **方向**：只用横向边界。正常网页上双方向无收益，引入纵向反而稀释 separation（tallgrid σ=10 从 9/9 掉到 0/9）。
- **状态**：不是完美。核心目标（消灭静默错位）从 254 帧降到 2 帧，但代价 5.3× DMS、拒绝率高、仍有 2 帧周期残留。
- **对比 DMS**：DMS 快 5.3×、接受多 29%，但 **90 次把内容放到错误位置且不告知用户**（全部来自 `seamAppend`）。本设计用「红框 + 冻结锚点」换掉了这 90 次静默损坏。

> **更新（2026-10-18 落地后）**：本文 §4 的数字来自实验原型。机制落地到生产代码后重新实测（同语料同真值，480 帧）：静默错位 **11**、跳变 **2**、单帧 **6.3 ms**（跟踪态）/ **4.2 ms**（滚轮态）。性能差距从 5.3× 缩小到 **2.5×**（6.3 vs 2.55），原因之一是落地时发现 `find_dirty_overlap_recovery` 每帧空跑 4.3 ms。详见 `docs/edge-stitch-design.md` §11。
